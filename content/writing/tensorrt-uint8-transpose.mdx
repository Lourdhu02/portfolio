## The cliff

The meter-OCR pipeline serves its models from Triton. Eight of the nine were TensorRT FP16 engines. The ninth, the classifier that decides whether a dial is digital or analog, still ran on ONNX Runtime.

That one model cost **309.5 ms** of compute per request, roughly 100× its TensorRT neighbours and around 96% of total request latency. Worse, throughput *fell* as load rose: at 16 concurrent requests the pipeline managed **19 img/s** with a p50 of **873 ms**.

## Why it was slow

ONNX Runtime assigns the graph's 33 `Shape` ops to the CPU and handles its 21 `InstanceNormalization` ops poorly, so every request bounced between host and device. The obvious fix was to build a TensorRT engine like the others.

TensorRT refused. The model takes raw UINT8 pixels (96×288×3) and its very first node is a `Transpose` on that UINT8 input. TensorRT wants the cast to float to come first.

## The patch

Retraining or moving the transpose to Python on the host would both have cost something. Instead, `build/patch_classifier_onnx.py` rewrites the exported graph: `Transpose → Cast` becomes `Cast → Transpose`. The two are numerically identical, and TensorRT accepts the second. The build script runs the patch automatically, so nobody has to remember it.

## Results

Same box, same 16 concurrent requests:

- **Classifier compute**: **309.5 ms → 3.3 ms** (94×).
- **Single-image p50**: **873 ms → 47 ms**.
- **Throughput**: **19 → 321 img/s**, and it no longer falls as load rises.

These were measured on the GB10 development box. On the production NVIDIA L4 the full pipeline sustains **181 img/s**, where the ceiling is the host CPU rather than the GPU.

## The lesson

One model left on the wrong runtime can own almost all of your latency while looking like a rounding error in the architecture diagram. Profile per stage, not per request.
