## The Incident

After a release of the SVTRv2 reader, readings with repeated digits started coming back short. A meter showing `4777.1` was decoded as `47.1`. Nothing crashed and the confidence scores looked healthy, which is exactly what made it dangerous.

## Root Cause

The recognizer emits one prediction per time step, and CTC decoding turns that frame sequence into text with two rules:

1. Identical consecutive tokens collapse into one.
2. A **blank** token (`ε`) separates genuine repeats, so `7 ε 7` means two sevens.

The regression updated the "previous token" only on non-blank frames, so a blank never broke a run:

```python
# The regression: blanks are skipped before prev is updated
for token in frames:
    if token == blank_id:
        continue
    if token != prev:
        decoded.append(token)
    prev = token
```

For the frames `4 ε 7 ε 7 ε 7 ε 1`, `prev` stays `7` across every blank, so the second and third sevens are dropped as "repeats".

## The Fix

Let the blank update `prev` like any other frame. It never emits a character, but it resets the repeat check:

```python
# The fix: every frame updates prev, blanks included
for token in frames:
    if token != blank_id and token != prev:
        decoded.append(token)
    prev = token
```

This is the decoder that runs in production today.

## Production Safeguards

1. **A fixed test set every release must reproduce**: 3,965 labelled images. Reading accuracy on its 2,950 meter photos must come out at exactly 83.4% before a change ships; any deviation means something moved and has to be explained.
2. **Regression tests**: 211 API and router tests run on every change.
3. **A router that cannot make callers worse off**: deterministic sha256 bucketing between the GPU path and the serverless path, fallback on any error or a 4-second timeout, and a circuit breaker after 5 consecutive failures.
